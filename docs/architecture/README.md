## Legend and evidence rules

**Implemented** means the named capability has a code path and supporting tests in this snapshot. **Partially implemented** means useful code exists but the functionality area's workflow or criteria remain incomplete. **Proposed** means the workflow is absent; a proposed component is an engineering recommendation for extending the existing application, not approved scope or a new customer rule. These labels do not replace workbook status or the team's Definition of Done. Tests linked here are evidence locations, not claims of a fresh passing test run.

The diagrams use Mermaid flowcharts with C4 levels, named boundaries, responsibilities and technologies. They are logical views, not hosting or deployment diagrams. Solid arrows describe current calls/relationships; dotted arrows describe source imports where labelled `imports`, or proposed integration where labelled `proposed`. Proposed nodes have dashed borders and explicit labels. Shared JavaScript is code loaded by each application, never an independently running service. Evidence links sit below diagrams so they work in Markdown viewers without Mermaid click support.

Requirements follow [repository guidance](../../AGENTS.md): latest explicit team decisions within team-controlled choices; later customer clarification; earlier clarification; Week 4 Project Instructions and original briefing; operational backlog/Sprint records; engineering recommendations. Team decisions cannot override confirmed customer requirements. The [effective requirements](../requirements/effective-requirements.md) reconcile the [briefing](../requirements/customer-briefing.md), [Session 1](../requirements/clarification-session-1.md) and [Session 2](../requirements/clarification-session-2.md). Their historical records are preserved. The Week 4 original is course material retained outside the repository; its actionable scope is recorded in effective requirements §2.

## Discrepancies and open decisions

1. **Stale overview text.** The [root README](../../README.md) says the drafts list/submission are absent and status transitions are future work. [Project context](../../project_context.md) still includes prototype-era route lists, incomplete-submission claims, “No CI workflow”, and an SPM-8 note saying no resubmit action exists. The current [routes](../../backend/src/routes/eventRequestRoutes.js), [frontend router](../../frontend/src/App.jsx), [transition service](../../backend/src/services/statusTransitionService.js) and [CI workflow](../../.github/workflows/ci.yml) contradict those statements; later context entries also supersede some earlier ones. This review records the discrepancy without rewriting historical evidence.
2. **Workbook status is not implementation evidence.** All seven selected Sprint 1 stories say Done; SPM-5/6/8/9/25/65 still say Not Started despite associated code/tests. SPM-63 has no status. No status is changed here. In particular SPM-42's organisation membership and downstream role surfaces must not be inferred complete from its Done cell.
3. **Workbook availability/grouping.** The workbook is untracked; no standalone Sprint Planning record was found. Venue Booking Approval has no separate Functionality Area group in the inspected workbook: SPM-34/54 sit under Venue Booking Request. The coverage table maps them to the required approval area without inventing a missing story ID. Extra criteria appear in the Priority column for SPM-25/45 and should be reconciled operationally.
4. **Cancellation criteria diverge.** Workbook SPM-47/63 introduce a before-start cutoff; SPM-47 also requires reasons, return/resubmit of cancellation requests, notifications and broader viewing. [Effective requirements](../requirements/effective-requirements.md) and [current policies](../../shared/cancellationRequests.js) apply no cancellation time boundary, allow an optional Organiser reason, and support request/approve/refuse only. Coordinator scope is assigned-only. No dated ratification of these additional workbook choices was found in the reviewed records. They remain a reconciliation issue, not silently adopted customer requirements.
5. **Rejection is incomplete against SPM-45.** [Reason action lists](../../shared/requestActions.js) omit Reject, so the existing rejection transition neither requires nor persists a rejection reason. No history reader supplies one to the Organiser. SPM-9's transition does not establish SPM-45 completion. *Update, 4 Oct 2026:* SPM-45 adds Reject to the reason-required actions and stores and displays a `rejection` record (effective-requirements.md §6).
6. **Pending or inconsistent decisions.** ER's later 1 October decision resolves Approved/Confirmed, but its closing decision list still lists that question. Submitted is the code constant while ER still records terminology ratification as unresolved. The assignment algorithm, explicit Start review action and clarification-message retention have pending labels in ER. Same-organisation visibility and Coordinator section breadth also have unresolved wording there; code uses company-ID viewing and all-section Coordinator edits. Equipment workbook rows prescribe individual IDs while ER leaves the model a team choice. Preserve these distinctions until the team records decisions.
7. **Incomplete integration.** No staff assignment, history UI, notification delivery, venue/equipment reservations, event registration or significant-change review exists. Seeded staff assignments make sign-off demos possible; newly created requests have no staff allocation path. Current minimal sign-off must not be described as venue booking approval or equipment reservation.

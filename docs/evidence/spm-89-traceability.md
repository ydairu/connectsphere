# SPM-89 acceptance traceability

Operational source: `docs/Product Backlog (2).xlsx`, `01_Product Backlog`, SPM-89, row 41 (Sprint 4). Its status is **In Progress**. The five criteria below come from that row; the per-venue rule also matches G8!C50 in `docs/requirements/effective-requirements.md` §5.3. SPM-48 supplies the preparation values and notes limit.

| Backlog criterion | Implementation | Verification |
|---|---|---|
| Each approved booking has its own status and notes using SPM-48 values | `venueBookingRequests/{bookingId}.preparation`, `shared/venuePreparation.js`; missing values read as Not Started and empty notes | SPM-89 unit and HTTP suites; Firestore emulator transaction suite |
| Assigned Venue Staff update one venue only in Preparation | `PATCH /api/requests/:id/venue-bookings/:bookingId/preparation`; the service re-reads event, booking and current booking set before its transaction writes | SPM-89 unit, HTTP, emulator and Chromium tests; direct refusals cover wrong actor, event, status and invalid values |
| Coordinator sees each venue and Ready only when every current approved venue and equipment are Ready | The booking list projects each current approved booking's preparation to the Coordinator; `eventPreparationReadiness()` requires at least one current approved booking, all of them Ready, and equipment Ready | SPM-89 unit, HTTP, page and Chromium tests; inactive and awaiting-reapproval attempts are excluded |
| Organisers and Attendees do not see preparation | Booking projection, event response and `visibleChangeHistory()` omit per-venue values for these roles; legacy event-wide values are no longer projected | SPM-89 HTTP and Chromium tests; SPM-48 and SPM-42 regressions |
| Each update is in change history with venue name | The booking transaction writes `field_changed` entries to the event's activity subcollection with booking ID and venue-name snapshot; the Coordinator's history renders the name | SPM-89 HTTP, emulator and Chromium tests |

The legacy event-wide `venuePreparation` value is kept in storage but is no longer editable through the event PATCH route. `backend/scripts/backfillVenuePreparation.js` is dry-run-first and idempotent: it copies a valid legacy value only when exactly one current approved booking exists and the booking has no value. Multi-venue and otherwise ambiguous records are reported for review. The script has **not** been run against the live project; no live data is claimed migrated.

Local verification on 31 October 2026: the focused SPM-89 and affected SPM-48/88/28/54/81/87/90 Vitest run passed 268 tests (12 opt-in cases skipped); the SPM-89 Firestore emulator suite passed 2 tests; and the SPM-89 Chromium journey passed. The full `npm test` run passed: 147 Node tests, 101 frontend tests, 2,277 Vitest tests (59 skipped) and 124 Chromium journeys. The amended migration and inactive-booking unit cases passed again after the full run began. Lint, production build and `git diff --check` passed. The HTTP suites use mocked identity and in-memory persistence; Chromium uses the local Firebase double; emulator tests use local Firestore. None is verification against the deployed Firebase project. Human acceptance, peer review, live migration, live API testing and CI results remain outstanding. Firestore rules were neither changed nor deployed.
